01 / VISÃO GERAL

Do navegador ao banco

O cadastro segue pelo Auth e pelo gatilho do banco. Depois do login, as consultas e operações seguem pela Edge Function.

01

Frontend + Auth

A tela usa Supabase Auth para cadastro e login. A sessão fornece o token do usuário.

02

Edge Function

Recebe a rota, exige autenticação, lê os dados e devolve JSON com o resultado ou erro.

03

Corretora

O serviço valida a operação e coordena os objetos e o acesso aos dados.

04

Repositório

Converte a ação em consulta Supabase ou chamada RPC e monta a resposta.

05

Postgres

Guarda as tabelas, limita a leitura por usuário e aplica operações transacionais.

A resposta volta pelo caminho inverso. A tela atual apresenta e-mail, ID da conta e saldo; as outras rotas ainda não têm controles visuais.

02 / CADASTRO E SESSÃO

Abrir conta é criar o cadastro

O usuário faz uma ação na tela. O Supabase Auth e o gatilho do Postgres cuidam das duas partes do cadastro.

1. Enviar cadastro

frontend/main.ts chama supabase.auth.signUp com e-mail e senha. A senha é tratada pelo Supabase Auth, não pela tabela contas.

2. Criar a conta

Quando nasce uma linha em auth.users, o trigger criar_conta_depois_do_cadastro insere uma linha em public.contas com saldo zero.

3. Confirmar e entrar

Se a confirmação de e-mail estiver ativada, o usuário confirma o endereço. Depois entra com signInWithPassword e recebe uma sessão.

Duas identidades ligadas por um ID: auth.users.id = contas.usuario_id. O campo usuario_id é único: cada usuário pode ter apenas uma conta da corretora.

Após o login

O frontend envia o token da sessão no cabeçalho Authorization: Bearer e a chave publicável no cabeçalho apikey.

Consulta da conta

GET /functions/v1/corretora/conta retorna saldo, posições e até 100 movimentações recentes. Hoje a tela exibe apenas saldo e ID.

Usuários antigos

Se um usuário anterior ao trigger não tiver conta, o frontend usa POST /conta como recuperação. A migração também tentou criar as contas que faltavam.

    Onde a POO aparece

    A Edge Function é a entrada HTTP. As classes dão nomes e responsabilidades aos conceitos do sistema.

    Dinheiro e QuantidadeValidam texto decimal e usam inteiros para evitar perda de precisão.
    Conta, Ativo, Posição e MovimentaçãoRepresentam os conceitos da carteira e produzem o JSON da resposta.
    CorretoraCoordena cada caso de uso. Recebe uma implementação da interface RepositorioCorretora no construtor.
    RepositorioSupabaseImplementa a interface e sabe consultar tabelas e chamar funções SQL.

    Conceitos POO: encapsulamento nas validações de Dinheiro e Quantidade; composição em Conta, que contém posições e movimentações; abstração e injeção de dependência na interface do repositório. O projeto não precisa de herança para aplicar POO.

    Rotas disponíveis na Edge Function

    Todas exigem uma sessão autenticada. A resposta é JSON. Os valores de dinheiro e quantidade são enviados como texto decimal.

    MétodoRota após /corretoraEntradaFunção
    GET/ativos—Lista o catálogo fictício.
    GET/conta—Consulta a própria conta.
    POST/conta—Recupera conta de usuário antigo.
    POST/depositos{"valor":"100.00"}Adiciona saldo simulado.
    POST/compras{"codigo_ativo":"ACAO1","quantidade":"2"}Compra ativo.
    POST/vendas{"codigo_ativo":"ACAO1","quantidade":"1"}Vende ativo.

    Cada RPC de depósito, compra ou venda roda como uma transação no Postgres. Se faltar saldo, ativo ou quantidade, a operação falha sem deixar uma alteração parcial.

    04 / BANCO DE DADOS

    O que fica salvo

    O Supabase Auth guarda o login. As quatro tabelas públicas da corretora guardam o catálogo, saldo, carteira e histórico.

    auth.users

    Usuário e autenticação, gerenciados pelo Supabase.

    id → contas.usuario_id

    contas

    Uma conta por usuário, com saldo em centavos.

    id · usuario_id · saldo_centavos

    ativos

    Catálogo compartilhado de ativos e preços fictícios.

    codigo · tipo · preco_centavos

    posicoes

    Quanto a conta possui de cada ativo.

    conta_id · ativo_codigo · quantidade_micros

    movimentacoes

    Histórico de depósito, compra e venda.

    conta_id · tipo · valor_centavos

    Quatro tabelas públicas: contas, ativos, posicoes e movimentacoes. RLS limita a leitura das informações pessoais ao dono da conta; o catálogo de ativos é compartilhado entre usuários autenticados.

    O cadastro cria a conta automaticamente por um trigger em auth.users. A Edge Function chama depositar, comprar e vender por RPC. A função abrir_conta continua disponível para recuperar usuários antigos sem conta.

    Dinheiro

    saldo_centavos, preco_centavos e valor_centavos são inteiros. Exemplo: R$ 25,00 é 2500 no banco.

    Quantidade

    quantidade_micros guarda até seis casas decimais. Uma unidade é 1000000 micros.

    Relações

    contas.usuario_id aponta para auth.users.id; posições e movimentações apontam para contas.id.

    05 / ISOLAMENTO

    Por que cada usuário vê sua conta

    A separação existe no banco e nas operações, não só na aparência da tela.

    Autenticação

    A Edge Function usa withSupabase({ auth: 'user' }). Sem sessão válida, a API não entrega a conta; uma chamada sem login foi verificada com resposta HTTP 401.

    Leitura com RLS

    A política de contas exige usuario_id = auth.uid(). As políticas de posições e movimentações verificam se a conta pertence ao mesmo usuário.

    Escrita pelas RPCs

    O cliente tem apenas permissão de leitura nas tabelas. As funções depositar, comprar e vender escolhem a conta a partir de auth.uid(), sem aceitar um ID de conta enviado pelo usuário.

    Limite da verificação atual: as políticas e permissões foram conferidas no projeto remoto, mas ainda falta um teste completo com duas contas reais tentando acessar os dados uma da outra.
